What the app keeps

See which details are saved with each sample error.

Sample errors are never uploaded to Sentry.

Only the details this demo needs

Each event comes from one of the three sample errors. The API does not accept custom errors, uploads or customer data.

Kept
Generated event ID, timestamp, fixed scenario message, release, service and normalized stack frame.
Discarded
User identity, email, IP, cookies, HTTP headers/bodies, query strings, hostnames, absolute paths, breadcrumbs and extra context.
Not enabled
Replay, profiling, automatic instrumentation, tracing, logs and client reports.
Retention
Last 200 local events and up to 20 examples per issue. Restart the app or clear the session to remove these records.

Sandbox / architecture

From sample error to inbox

This app uses the official Sentry SDK. The inbox and sample workflows are built for this demo.

01

Sample error

A sample function throws an error. The server catches it and prepares it for the SDK.

02

SDK capture

The official Node SDK generates an event and parses the exception stack. Automatic integrations are disabled.

03

Local transport

The app keeps only approved fields, checks them again and saves them in memory. It sends nothing to Sentry.

04

Issue workflow

Errors from the same scenario share one issue. Resolve it, then capture it again to see it reopen.

What this is

A small app using @sentry/node, with its own inbox, data checks and tests.

What it doesn't reproduce

Sentry's ingestion service, grouping algorithms, distributed tracing, multi-user permissions, storage platform, alerts and production scale. The local inbox is a teaching tool.
